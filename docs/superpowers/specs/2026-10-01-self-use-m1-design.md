# 月笺自用版 M1 产品、数据与验收规格

日期：2026-10-01
状态：当前 M1 权威规格，待实现与验收
适用范围：Android 首发；服务端 API 为后续 iOS 保持兼容
取代范围：取代 `2026-09-30-couple-diary-design.md` 中所有 M1 范围、同步、身份与验收定义；旧文档仅保留长期产品愿景和历史决策参考。

## 1. 产品结论

月笺是一款只服务于一对伴侣的私密记录工具，但不能以“双方必须同时参与”为使用前提。任何一方都应能独立记录、回看和保管自己的生活；当另一方加入后，双方在同一条时间线上看到彼此发布的记录，并可用各自身份补充共同回忆。

M1 的成功标准不是页面数量，而是一条真实、可恢复、可验证的数据闭环：

`设备 A Room → 持久化 Outbox → HTTP → PostgreSQL → Change Feed → 设备 B Room`

这条链路必须先以个人纯文字记录贯通，再接入共同记录、评论、图片与完整视觉界面。

## 2. 产品原则

- 不监控位置：只允许主动选择城市或请求一次位置快照，不保存实时位置和轨迹。
- 不制造关系压力：不做签到、连续天数、活跃排名、催促伴侣记录等机制。
- 不让 AI 代写回忆：M1 不生成、改写或总结用户内容。
- 数据可完整带走：用户数据不得被锁在应用中，备份、恢复和导出是产品能力而非售后补丁。
- 一个人也能使用：未配对、伴侣暂未参与或暂时离线时，个人记录仍可正常创建和回看。
- 真实可靠优先：不能用演示数据、假服务或相同字符串断言替代真实双端验收。
- 记录成本优先于功能数量：书写摩擦用缺失的日子付账，错过的一天无法补写。进入记录不选媒介类型、无必填字段、自动保存。
- 连续性优先于完整性：TA 必须能在维护者不在场时使用它；断掉之后要能自己接上，而不是等人修。
- 使用者拥有它：App 内称呼、双方身份色、首页封面和页面措辞由使用者决定，参考图和规格让位。这种决定权体现为**随时能在应用内改**，不体现为使用前必须先选——默认值必须开箱即用（§8）。
- 重新相遇早于扩展：回看旧记录是本产品的情感回报来源，不作为后续里程碑的锦上添花。

长期取舍依据见 `docs/human-scale-principles.md`；当范围需要取舍时，按该文件第 9 节的顺序让路。

## 3. M1 范围

### 3.1 必须完成

1. **可启动的服务端**：配置明确，能连接 PostgreSQL，健康检查和数据库迁移可验证。
2. **轻量双人身份**：首位使用者通过部署密钥初始化空间；生成一次性配对凭据邀请另一人；最终每个空间最多两名成员。
3. **设备会话**：客户端使用不可猜测的长期设备令牌认证，不再信任客户端提交的任意用户 ID。
4. **个人文字记录**：离线创建、保存草稿、发布、编辑自己的记录、查看版本、删除和恢复；发布后伴侣可见，草稿只对作者可见。
5. **共同记录**：同一主题下并列展示双方视角；每人只编辑自己的内容块，所有发布修改保留版本；M1 不做跨作者文本合并和同块冲突解决。
6. **评论**：双方可对已发布记录评论；作者身份和精确时间明确。
7. **可靠同步**：前台启动、回到前台、手动刷新和网络恢复时同步；失败可重试，重复请求不产生重复业务结果。
8. **图片**：只在纯文字双端链路验收通过后接入；发布前必须确认对象上传完成。
9. **备份与恢复**：至少完成一次可验证的完整备份—清空测试环境—恢复演练。
10. **选择性导出**：按记录或时间范围导出结构化数据、可阅读文本和所引用的原始媒体。
11. **真实数据 UI**：首页、个人记录、共同记录和“我们”页只能读取 Room 真实数据，不以硬编码演示列表作为业务源。
12. **个人资料与主题**：允许修改自己的头像和名字；暖米色与纯白主题由双方各自选择。所有可定制项都必须**在应用内可达并可改**——默认值开箱即用，不要求使用者先配置才能开始记录，也不得把可定制项只实现为源码常量（改它需要重新构建的不算可定制）。可修改性要求见 §8。
13. **系统分享入口**：从相册或任意 App 的分享菜单把一张图片、一段文字直接变成一条待编辑记录，不需要先打开月笺、不需要先选择媒介类型。接住已经在发生的交换，优先级高于任何编辑器增强。
14. **每周回看**：在固定时间（默认周日晚上，可关闭）呈现一条明显更早的记录，只选一条、不聚合、不评分、不用 AI 生成。找不到符合条件的记录时安静跳过，不制造空内容。
15. **会话恢复路径**：在两台设备都不可用（换机、重装、丢机）时，仍有一条不依赖旧设备、不依赖配对凭据重新签发有效会话的恢复手段，且该手段与备份放在同一位置并演练过。
16. **轻量新记录提醒**：对方发布新记录时给一次本地通知，内容不含正文。它只在客户端同步完成后触发，不依赖 FCM，不属于后台秒级承诺。

### 3.2 同步时效承诺

- 应用在前台且网络正常时，目标是一次同步周期内让另一端看到更新。
- Android 后台执行受系统调度和省电策略影响，M1 不承诺“后台秒级”或“一分钟内必达”。
- FCM 可在后续作为“提醒客户端拉取”的优化，不携带正文、媒体地址、坐标或其他私密内容，也不是 M1 正确性的前提。

### 3.3 暂缓但不删除的需求

以下能力保留在产品路线图中，只有在纯文字真实双端闭环通过后才能排期：共同相册、视频、语音、音乐分享、城市地图、倒计时与纪念日、时间胶囊、过去的今天、本周小结。相册与地图在 M1 可以呈现清晰的“尚未开放”状态，不得标记为已完成。

这里被暂缓的「本周小结」指把多条记录累计、概括或评分成一份周报。**3.1 第 14 条的「每周回看」不属于被暂缓项**：它只在固定时间原样呈现一条明显更早的记录，不聚合、不生成、不评分，是 M1 必须完成的能力。

### 3.4 提醒与统计边界

原则是**单次信号可以有，聚合统计不能有**。温度来自"TA 写了东西"，压力来自"TA 这个月只写了两条"。

允许：

- 对方发布新记录时的一次本地提醒（见 3.1 第 16 项）；
- 一条记录被对方看过时的一次性、不累积、不列表化的轻量标记。

明确不做，且不得以"设置项""调试功能"或"本地统计"的形式实现：

- 任何一方的记录条数、字数、活跃天数、间隔天数的统计、排名或趋势；
- 已读回执的历史列表，或"谁在何时打开过什么"的展示；
- "对方很久没写"任何形式的提示、催促或暗示；
- 双人进度、共同成就、目标完成度；
- 评价性或比较性的周总结（只允许事实回顾）。

### 3.5 记录成本度量

记录成本是产品能力，不是体验偏好，因此必须量化并要求证据：

- 从解锁手机到一条纯文字记录保存成功，目标 **≤ 10 秒**、**≤ 4 次交互**；
- 点击 `＋记录` 直接进入文字书写态，不出现媒介类型选择、不出现必填字段；
- 从系统分享入口进入时，一张已存在的照片变成一条可编辑记录不超过 2 次交互；
- 草稿自动保存，无需显式保存动作，进程被杀不丢正文；
- M1 验收必须在两台目标真机上各计时一次并记录实际秒数与交互数。

## 4. 信息可见性与编辑权限

| 内容 | 作者 | 伴侣 | 修改规则 |
|---|---|---|---|
| 个人草稿 | 可见 | 不可见 | 仅作者 |
| 已发布个人记录 | 可见 | 可见、可评论 | 正文仅作者，保留版本 |
| 共同记录中的作者视角 | 可见 | 可见、可评论 | 每人只改自己的块，保留版本 |
| 评论 | 可见 | 可见 | 仅评论作者可删除；M1 不编辑评论 |
| 头像与名字 | 可见 | 可见 | 只能修改自己 |
| 本机主题 | 可见 | 不覆盖对方 | 仅影响本机 |

所有业务读取和写入都必须同时校验“已认证设备会话”和“所属双人空间”；知道 UUID 不能成为访问权限。

## 5. 身份与配对

M1 不建设邮箱、手机号、密码找回和管理员后台，但必须具备真实认证边界。

### 5.1 初始化

- `POST /api/v1/bootstrap` 仅在数据库中还不存在用户时可执行。
- 请求必须携带部署环境变量 `BOOTSTRAP_SECRET`；服务端不得提供默认生产值。
- 成功后创建双人空间、首位成员和首个设备会话，返回一次性展示的 bearer token。
- 初始化完成后，该接口永久拒绝再次创建首位用户。
- bootstrap 成功后 `BOOTSTRAP_SECRET` 必须立即失效（服务端标记已消费，不再接受该值）。否则在"删库重建"场景下——这正是 §7 恢复演练会做的事——任何能访问该端口的人都可以重跑 bootstrap 占据空间。恢复演练必须同时验证"已消费的 bootstrap 密钥再次使用被拒绝"。

### 5.2 配对

- 已认证的首位成员创建一次性配对凭据。
- 凭据使用至少 128 bit 的加密安全随机值，默认 15 分钟过期，成功使用后立即失效。
- `POST /api/v1/pair` 创建第二位成员和设备会话；空间已有两人时拒绝。
- 不使用可枚举的六位数字作为唯一配对秘密。

### 5.3 设备令牌

- API 统一使用 `Authorization: Bearer <token>`。
- 数据库只存令牌哈希、用户、空间、创建时间、最后使用时间和吊销时间。
- M1 每名成员只保留一个有效设备会话，即一个空间恰好最多两个有效长期 token；换机通过吊销旧 token 并签发新 token 完成，不扩展为多设备账号系统。
- Spring Security 关闭表单登录和 HTTP Basic，只允许明确列出的公开端点。
- `X-User-Id` 不能参与生产认证，相关兼容入口必须删除或限定为测试代码。

### 5.4 会话恢复与锁死防护

按 5.1–5.3，吊销旧会话和签发新会话都需要一个已认证的会话，bootstrap 只在空库可执行，配对凭据只能由已认证成员创建。这构成一条死路径：**两台设备同时不可用（换机、系统重置、丢机、重装）时，使用者将无法重新进入自己的存档。** 对自托管私密档案，这是最高优先级的风险，高于任何同步正确性问题。

必须提供一条不依赖任何旧设备、不依赖网络的恢复手段：

- 服务端本地管理命令（优先）或一个需要独立 `RECOVERY_SECRET` 的管理端点，可列出并吊销现有会话、为指定成员签发新会话；
- 该命令只在服务端所在机器上可执行，或不通过公网可达；`RECOVERY_SECRET` 与 `BOOTSTRAP_SECRET` 必须是不同的值；
- 每次会话签发、吊销和恢复都写入一条不含令牌内容的审计记录（时间、成员、动作），便于发现异常进入；
- 恢复步骤、命令文本和密钥存放位置**与备份介质放在一起**；恢复演练必须真实执行一次"吊销全部会话 → 用恢复命令重新进入 → 双端拉取一致"，并记录命令与退出码；
- 恢复能力不得演变为多设备账号系统：M1 仍然每名成员最多一个有效会话。

对使用者一侧的要求：服务端不可达、凭据过期或需要恢复时，客户端必须明确告知"你的本地记录仍然完整可读，联网后会自动继续"，不得出现无法自助理解的死状态。

## 6. 数据与同步规范

### 6.1 客户端本地写入

- UI 的业务数据唯一来源是 Room。
- 每次本地业务变更和对应 outbox 操作必须在同一个 Room 事务提交。
- outbox 使用 UUID v7 `operation_id`，记录操作类型、业务对象 ID、规范化 payload、创建时间、尝试次数和状态。
- 拉取一页变更时，业务数据更新与本地 cursor 更新必须在同一个 Room 事务提交；失败则两者都不前进。

### 6.2 服务端写入

- 客户端只能提交服务端支持的强类型操作，例如 `CREATE_PERSONAL_ENTRY`、`PUBLISH_ENTRY`、`UPSERT_OWN_SHARED_BLOCK`、`ADD_COMMENT`、`UPDATE_OWN_PROFILE`（称呼、头像、本人身份色走同一条幂等链路，不设旁路端点）；禁止客户端直接写入任意 change-feed payload。
- 同一数据库事务必须完成：认证与成员校验、幂等键占位、业务写入、版本快照、空间序列分配、change row 写入和幂等响应保存。
- 幂等性按 `(couple_id, operation_id)` 生效；相同 ID 和相同 payload 返回原响应，相同 ID 和不同 payload 拒绝。
- `media` 只有处于 `READY` 且属于当前空间时，才能被发布记录引用。

### 6.3 有序变更流

全局数据库 identity 不能作为空间同步正确性的依据。每个双人空间维护独立的同步状态：

```text
couple_sync_state(couple_id PRIMARY KEY, next_sequence BIGINT NOT NULL)
change_feed(couple_id, space_sequence, entity_type, entity_id, change_type, payload, committed_at)
UNIQUE(couple_id, space_sequence)
```

业务事务在写入 change row 前锁定所属 `couple_sync_state` 行、递增 `next_sequence` 并分配序号。这样同一空间内序号分配和事务提交被串行化，客户端才能安全地把已完整应用的最大 `space_sequence` 作为游标。

服务端按 `(space_sequence ASC)` 分页；响应包含 `changes`、`next_cursor` 和 `has_more`。客户端不得根据本机时间推导游标。

### 6.4 核心数据模型与格式约束

| 聚合/实体 | 必需字段 | 核心约束 |
|---|---|---|
| `couple_space` | `id`, `created_at` | 最多两名有效成员；业务数据必须带 `couple_id` |
| `app_user` | `id`, `couple_id`, `display_name`, `avatar_media_id` | 只能修改自己的资料；名字去除首尾空白后 1–40 个 Unicode 字符 |
| `device_session` | `id`, `user_id`, `couple_id`, `token_hash`, `created_at`, `last_used_at`, `revoked_at` | 每名成员最多一个有效会话；不存明文 token |
| `entry` | `id`, `couple_id`, `mode`, `state`, `occurred_at`, `occurred_timezone`, `author_id`, `current_revision`, `deleted_at` | `mode` 仅 `PERSONAL/SHARED`；草稿不进入伴侣 change feed |
| `entry_block` | `id`, `entry_id`, `author_id`, `type`, `order_key`, `payload`, `media_id`, `block_version`, `deleted_at` | M1 `type` 先支持 `TEXT/IMAGE`；共享块不可跨作者修改 |
| `entry_revision` | `id`, `entry_id`, `revision_no`, `editor_id`, `snapshot`, `created_at` | `(entry_id, revision_no)` 唯一；发布修改只追加，不覆盖历史 |
| `comment` | `id`, `entry_id`, `author_id`, `body`, `created_at`, `deleted_at` | 正文去除首尾空白后 1–1000 字符；删除保留审计时间 |
| `media_asset` | `id`, `couple_id`, `owner_id`, `state`, `object_key`, `mime_type`, `byte_size`, `sha256` | `READY` 前不可发布引用；对象 key 由服务端决定 |
| `idempotent_operation` | `couple_id`, `operation_id`, `payload_hash`, `status`, `response`, `created_at` | `(couple_id, operation_id)` 唯一；payload hash 不同则拒绝复用 |
| `change_feed` | `couple_id`, `space_sequence`, `entity_type`, `entity_id`, `change_type`, `payload`, `committed_at` | `(couple_id, space_sequence)` 唯一；只由业务事务生成 |

跨端格式统一如下：

- 业务对象、操作和 change 标识使用 UUID v7 的小写标准字符串；服务端仍必须校验归属，不能依赖 UUID 难猜。
- API 时间戳使用带 `Z` 的 ISO-8601 UTC；故事发生地时区单独保存 IANA 名称，例如 `Asia/Shanghai`。
- `occurred_at` 表示故事发生时间，`created_at/updated_at/committed_at` 表示系统事实，不能互相覆盖。
- JSON 字段使用 `snake_case`；未知枚举值客户端不得崩溃，应保留原始记录并提示升级。
- 正文按 UTF-8 保存；M1 单个文字块最大 20,000 个 Unicode 字符，服务端和客户端使用同一限制。
- 所有删除先形成可同步的墓碑；物理清理必须晚于所有活跃设备的安全窗口和备份保留期。
- change payload 只包含重建客户端读取模型所需的数据，不包含 bearer token、配对秘密、存储密钥或长期有效下载 URL。
- **未实现的能力不得占用可写入的枚举值。** `entry.state` 中尚无实现规则的取值（如胶囊锁定、归档）必须从数据库枚举和服务端 DTO 中移除，等到对应里程碑再作为 migration 引入。暴露一个能被写入但没有读取路径约束的状态，等于暴露一个数据黑洞；当前 `CAPSULE_LOCKED` 正是这种状态。
- **不可逆操作必须有冷静期。** 删除整条记录、删除全部记录、解散空间这类动作，默认进入 24 小时可撤销的待删除态，期间双方都能看到且都能撤销；到期后才形成同步墓碑。这是一条产品要求，不是备份策略。
- **真实内容出现后迁移纪律立即生效。** 一旦两台真机开始写真实记录，此后所有 migration 必须向后兼容或具备演练过的回滚，并且必须先在一份含真实数据的副本上执行一遍。"反正是测试库"这句话在此之后不再适用。

### 6.5 现有迁移与本规格的对齐清单

仓库中的 V1–V5 迁移和现存服务代码与本规格存在下列差异。实现方**不得自行选择一侧覆盖另一侧**：以本规格为准修改迁移，遇到需要改动已有数据的情形先回传说明。

| 项 | 现有实现 | 本规格 | 处理 |
|---|---|---|---|
| `entry.mode` | 枚举 `PERSONAL/COLLABORATIVE` | `PERSONAL/SHARED` | 收敛枚举；`CAPSULE_LOCKED`、`ARCHIVED` 一并移除 |
| `app_user.display_name` | 无此列，`user_profile.display_name` 限 1–24 | `app_user` 持有，1–40 码点 | 确认 40 是否为有意放宽；若保留 40，需同时检查 UI 名字区宽度与截断 |
| `comment.body` 长度 | 1–2000 | 1–1000 | 以本规格为准收窄，并同步服务端校验 |
| `idempotency_record` | 主键 `operation_id` | `(couple_id, operation_id)` 唯一 | 需要带数据搬运的 migration，不只是建新表 |
| `change_feed` | 全局 identity `change_seq` | `(couple_id, space_sequence)` | 见 §6.3，旧列不得继续作为客户端游标 |
| 配对秘密 | 六位数字 `space_pairing_code` | ≥128 bit 随机值 | 删除旧机制，不留双轨 |
| 媒体状态 | `S3ObjectStorage.head()` 无条件抛异常 | `READY` 才可被发布引用 | 需真实对象存储实现，占位实现不得进入验收 |

## 7. 备份、恢复与导出

### 7.1 完整备份

备份首先是一种**持续运行的能力**，其次才是一次演练。自托管存档的真实风险不是"没备份过"，而是"备份脚本在某天静默失败，三个月后才发现"。

运行时要求（M1 必须成立）：

- 备份包含 PostgreSQL 业务数据、对象存储原始媒体和一份带版本号的 manifest；
- manifest 至少记录 schema 版本、生成时间、空间 ID、对象数量、媒体校验和和应用版本；
- **每日自动执行**，不依赖维护者在线或记得操作；
- 每次成功备份向服务端写入一行可查询的健康记录（时间、规模、校验摘要）；连续失败必须在维护者下次进入时明确显示，而不是只写日志；
- 对象存储启用版本控制或等效防误删能力；
- 至少一份**不在这台服务器上的副本**（另一块磁盘、另一个账号或另一个厂商），且与服务器凭据不共享同一把钥匙；
- 备份介质本身装着全部私密内容与媒体，必须加密存放并具备独立访问控制；泄露面不能只是从服务器转移到备份目录；
- 手机双端副本不算备份。

演练要求：

- M1 验收必须在隔离测试环境完成一次完整恢复，核对记录数、评论数、版本数、媒体数和随机抽样校验和；
- 此后每季度至少演练一次，演练记录落在 `docs/testing/`；
- 演练必须同时覆盖 §5.4 的会话恢复，即"恢复出来的存档能被重新签发的会话正常进入并使用"。

### 7.3 存档可读性与主数据表示

自托管系统的寿命通常等于维护者的耐心，而不是代码质量。目标不是"服务永远在线"，而是"**在任何一台电脑上都能重新打开这份档案**"。

因此：

- 导出产物必须能在不依赖本项目任何代码的前提下被阅读——浏览器打开索引、纯文本读内容、常见图片格式直接可见；
- 导出格式版本化，且在格式变更时保留旧格式的解析说明；
- 导出不得依赖服务端仍在运行：在服务器完全不可达时，客户端本地缓存的内容必须仍可读、仍可另存。

**待产品所有者决定，实现方不得自行选择：** 主数据表示采用哪一种。

- 方案 A（当前默认）：PostgreSQL 是权威数据源，导出为强制能力，接受"服务停摆期间只能读客户端缓存"。
- 方案 B：文件集合（Markdown/JSON + 原始媒体目录）本身是权威，数据库只是索引。它会把幂等键、游标并发、序号分配这一整族难题降级为"两个写作者往一个只追加的文件集合里写"，代价是失去强事务与关系约束，并且需要另设并发写入规则。

本节被改写之前，一律按方案 A 执行。这是一个会显著改变架构的取舍，必须先定，再动工 §6。

## 8. 视觉与交互基线

六张参考稿给的是方向——手帐质感、连续缝线时间轴、双身份色层级——不是像素基线；不得将整张参考图作为页面背景：

| 页面 | 方向参考 | M1 状态 |
|---|---|---|
| 时光首页 | `docs/design/reference/home-timeline.png` | 必须接真实数据并验收 |
| 我的记录 | `docs/design/reference/personal-entry-editor.png` | 必须接真实数据并验收 |
| 共同记录 | `docs/design/reference/shared-entry-editor.png` | 必须接真实数据并验收 |
| 我们 | `docs/design/reference/couple-profile.png` | 必须完成基本资料与主题 |
| 共同相册 | `docs/design/reference/shared-album.png` | M1 可为明确占位 |
| 城市地图 | `docs/design/reference/city-map.png` | M1 可为明确占位 |

硬性规则：

- 首页是左侧缝线式、可一滑到底的连续时间轴，不按天分页。
- 首页封面可替换；中秋只作为少量纪念元素，不做整套节日皮肤。
- 底部导航固定为 `时光 / 相册 / ＋记录 / 地图 / 我们`；编辑器内不显示主导航。
- 个人记录采用自然书写界面；共同记录采用并列的双视角内容块，并显示双方身份和具体时间。
- 默认暖米色，提供纯白主题；只替换颜色与纸张表面，不改变结构。
- 功能图标统一使用细线描边体系；禁止混用 emoji、填充图标和随意手绘符号。
- 中文正文不低于 14sp，触控目标不小于 48dp；键盘和大字号不能遮挡发布操作。
- 390 × 844 是截图对比基准，不是固定布局尺寸；其他 Android 尺寸必须正常重排。
- **可修改性是产品能力，不是空白。** 名称、身份色、封面、主题和页面措辞都要有开箱即用的默认值，并且使用者能在应用内改掉，不依赖重新构建、改文件或维护者介入。改动不得破坏已写入的内容。
- **只有单向门需要提前定。** 提前决定并写死的范围限于：导出格式与文件名约定、身份与恢复机制、真实内容出现后的数据语义，以及下面这条 Android 限制。其余偏好项一律留成可改，不要求使用者在开始记录前先表态。
- Android 桌面图标名称由 launcher 在安装时读取，使用者无法自由输入；只能用预先声明的有限候选（`activity-alias`）或在下一版构建中定名。因此"名称归使用者"在本规格里如实表述为：应用内称呼、封面、身份色与措辞自由，桌面图标名提供候选并向使用者说明这一项为什么受限。

视觉验收只能在真实数据链路完成后进行，并且验收现场是**真实设备**（按 §9 第 7 条：至少一台真实 Android 手机，配对端可用具名模拟器但须写明），不是模拟器与参考稿的并排截图。参考稿给出的是方向（手帐质感、连续缝线时间轴、双身份色层级），不是像素基线——它们与本仓库的骨架代码产出自同一天，把"复刻自己未经检验的想象"当成完成标准是一种空转。判断标准是三条：**像纸、像使用者自己的、不像软件。**

同一内容状态下逐屏对照并记录结构、间距、颜色、文字、图标、滚动与遮挡差异；同时在两台目标设备（§9 第 7 条）上实测 §3.5 的记录成本、键盘弹出、小屏重排和大字号可达性。

决定权归属：应用内称呼、双方身份色、首页封面和页面措辞默认值由使用者选择，参考稿和本规格在此让位（桌面图标名按上面的 Android 限制给候选）。默认值照旧开箱可用，选择权体现为"随时能改"，不体现为"使用前必须先选"。给使用者两个具体版本二选一，不提供成品征求意见。

## 9. M1 验收定义

M1 只有同时满足以下条件才能标记完成：

1. 服务端在干净环境以明确配置启动，迁移成功，健康检查通过。
2. 使用真实 PostgreSQL 和随机端口 Spring Boot，两个独立 bearer token 通过真实 HTTP 完成写入与拉取；测试不得直接调用 service，也不得使用内存 FakeServer 冒充端到端。
3. 两个独立 Room 数据库分别代表设备 A、B；A 离线写入后，经 outbox/HTTP/change feed 在 B 的 Room 出现，UI 从 B 的 Room 读取。该条的**主要证明场所是 JVM 上的 Robolectric 夹具**：两个真实 Room 数据库文件 + 真实 Retrofit + 真实 Spring Boot + 真实 PostgreSQL；假服务、内存 store 和常量游标一律不计。UI 侧的读取真实性在计划 Task 11 的设备冒烟和 Task 14 录像中复核。
4. 覆盖超时重试、重复 operation ID、进程重启、逆序重连、分页拉取、无权限 UUID 和游标事务回滚。
5. 双方并发补充共同记录时，各自视角均保留；任何人不能修改对方的内容块。
6. 完成备份恢复演练与选择性导出检查。
7. 证据分两层，缺一不可：
   - **数据链证据**：JVM 双 Room 夹具与真实服务端 E2E 的完整命令、退出码、通过/失败数、commit 与日志；
   - **设备证据**：至少一台真实 Android 设备完成安装、登录、书写、同步和录像，四个 M1 页面的视觉对照必须在真实设备上进行。配对的另一端优先使用第二台真机；确实无法提供时，可用具名模拟器代替，但必须在验收记录写明用的是真机还是模拟器、设备名与 Android 版本。需要真实系统能力的条目（系统分享面板、通知到点、键盘与触控成本）不得用 JVM 夹具代替。
8. 四个 M1 页面在真实设备上通过视觉复核：以 §8 的三条判据（像纸、像使用者自己的东西、不像软件）为准，参考稿是方向而非像素基线；相册和地图明确显示未开放，不伪装为完成。
9. **系统分享入口**：从相册或其他 App 分享一张图片/一段文字，能在目标真机上生成一条可编辑记录并走通同一双端链路。
10. **每周回看**：在两台目标设备（按第 7 条的定义，优先真机，用模拟器须写明）上各验证一次——到点在固定时间呈现一条明显更早的记录，无记录时安静跳过，可一键关闭，且不含任何生成内容。
11. **会话恢复**：执行一次"吊销全部会话 → 用恢复命令重新签发 → 双端重新拉取一致"，记录命令、退出码与结果。仅"备份文件存在"不算通过。
12. **备份作为运行能力**：自动备份在连续至少 7 天内每日产生健康记录行，演练一次从该备份完整恢复；同时确认对象存储版本化已启用、存在一份不在同一台机器上的副本。
13. **记录成本**：在两台目标设备上各计时一次（至少一台为真实手机，另一方按第 7 条可用具名模拟器但须写明设备与 Android 版本），从解锁到一条纯文字记录保存成功的实际秒数与交互数写入验收记录，目标 ≤ 10 秒、≤ 4 次交互。键盘和触控相关证据不得用 JVM 夹具代替。

### 9.1 开始使用与观察

验收不是使用的起点。**个人文字竖切（计划 Task 11）通过之日，就是两台真机开始写真实记录的日期**，带着当时已知的全部缺陷开始。延后一天开始，就少一天真实记录，而这份档案的价值只按天累积。

由此产生两条约束：

- 真实内容一旦写入，§6.4 的迁移纪律立即生效，此后不得以"测试库"为由丢弃数据；
- 唯一的观察指标是**未经提醒的自发打开次数**（分别按设备记录，不展示给对方，不做任何统计或排名的界面呈现，只作为维护者自己的判断依据）。"对方说挺好"不作为任何决策依据。

单元测试、Repository 测试、API 映射测试和假服务场景仍有价值，但只能作为组件级证据，不能单独支持“M1 已完成”结论。

## 10. 明确不做

- 公开社交、群组、关注和陌生人发现。
- 实时位置、后台持续定位和行动轨迹。
- WebSocket 实时协同、多人光标、CRDT 和跨作者块合并。
- 复杂账号中心、邮箱/手机号注册、运营后台。
- AI 代写、AI 总结、关系评分和行为提醒。
- 关系记分牌：任何一方的记录数量、字数、活跃与间隔天数的统计、趋势、排名或仪表盘（§3.4 的禁止项不得以设置开关、调试入口或"只在本地统计"的形式绕过）。
- 在纯文字双端闭环未通过前并行扩张视频、语音、地图或复杂相册。
