# 开档手册（真实内容的第一天）

编写日期：2026-10-01
适用对象：拿着一台开发机、两台手机和这个仓库的人。**这一天由使用者决定，不由代码决定。**

> 「开档」＝清掉或封存测试数据，伴侣正式加入，从「我们的第一页」开始写真实记录。
> 这一天的意义在于：**从这一刻起，迁移纪律、备份纪律和「不能丢」的判据全部生效**（规格 §6.4、人类尺度原则第 6 节）。之前丢的是测试数据，之后丢的是回忆。

---

## 0. 前一晚就能做的准备（不碰手机）

1. **确认绿色基线**：`bash scripts/verify-m1.sh`。本机没有 Android SDK/真机时它会以 `INCOMPLETE` 退出并报出缺什么——那不算通过，只是允许你继续往下走。当前开发机的实测数字（2026-10-01 复跑）：服务端 63 项、Android 74 项 JVM 单测全绿、0 失败，`:app:assembleDebug` 成功。
2. **封存现有数据**（已经做过一次，开档当天核对即可）：
   ```bash
   MSYS_NO_PATHCONV=1 docker exec -t infra-postgres-1 \
     pg_dump -U moon_letter -d moon_letter -Fc -f /tmp/moon_letter.dump
   MSYS_NO_PATHCONV=1 docker cp infra-postgres-1:/tmp/moon_letter.dump \
     "E:/MoonLetter/archive/pre-open-$(date +%F)/moon_letter-pre-open.dump"
   ```
   仓库外的归档目录（`E:/MoonLetter/archive/`）保存导出，**绝不提交进 git**。
3. **核对空间已经是"空档"状态**。开档当天的期望值是：内容全 0、成员和会话还在。
   ```sql
   select (select count(*) from entry)     as entry,
          (select count(*) from entry_block) as block,
          (select count(*) from comment)    as comment,
          (select count(*) from sync_change) as change_row,
          (select count(*) from media_asset) as media,
          (select count(*) from app_user)   as member,
          (select count(*) from device_session where revoked_at is null) as session;
   ```
   2026-10-01 实测：`entry=0 block=0 comment=0 change_row=0 media=0 member=2 session=2`。
   表名写错会让"前后计数"变成永远 0 的假绿，所以这组表名由 `SchemaTableNamesTest` 守住。
   **如果这里还有测试内容**：先备份副本再删，删除顺序 `comment → entry_block → sync_change → media_asset → entry`，保留 `app_user`、`couple_space`、`couple_member`、`device_session`，这样空间与配对关系不用重建。
   **但服务端空了不等于手机端干净**：直接删库的行不会变成变更流里的删除，手机各自的 Room 里那些行还在，时间线照旧显示。第 1 节第 1 步是唯一的清法。
4. **启动服务端**（命令与"为什么不能用 `mvn spring-boot:run` 传密钥"见 README §服务端）。手机和电脑必须在同一局域网，且 `http://<开发机 IP>:8080/actuator/health` 在手机上能打开。
5. **两台手机都装当天构建的 APK**。旧 APK 里没有恢复语义、Keystore 令牌、响应式时间线和通知，装它开档会在第一天就撞上已知会修的坑。

## 1. 当天：把两台手机接进同一个空间

顺序不能颠倒，因为配对码是一次性且 15 分钟有效。下面 1–4 步已经在 JVM 上按真 Room + 真服务端 + 真 PostgreSQL 跑通过一遍（验收记录 26：同一台手机清数据后用同一个密钥回到**同一个成员位**，并把空间里**全部**已发布记录、回应和称呼拉回来，旧令牌当场失效）。所以当天不是摸索，是把已证明的路径在真手上走一遍并留记录。

1. **两台手机都先清成干净状态**：设置 → 应用 → 月笺 → 清除数据（或卸载重装）。本机 Room 里那 5 条标题为 `u` / `h` 的键盘乱码草稿只能这样清掉——服务端早就删了，但删除不会顺着变更流走回去。**这一步会把会话令牌和服务器地址一起清掉**（令牌只存在应用私有目录里），所以手上要有：开发机局域网地址、`BOOTSTRAP_SECRET`。清除数据会丢掉未发布的本机草稿，开档当天这正是目的；那 5 条已归档在 `E:/MoonLetter/archive/pre-open-2026-10-01/`。**真实内容出现之后，绝对不要用这一步当清理手段。**
2. **第一位的那台**打开应用 →「我是第一位」→ 填服务器地址、称呼、初始化密钥。它会找回自己原来的成员位（同一个 `userId`、同一个空间，profile 上已有的名字不会被改写），而不是新建一个把伴侣挤掉的陌生人。
3. 「我们」页 →「换手机或重新配对」→「生成配对码」→ 把码传到另一台手机。每次新生成都让上一个作废，码 15 分钟有效且只用一次。
4. **另一台手机**打开应用 →「我是伴侣」→ 填服务器地址 + 粘贴配对码 →「配对加入」。空间里两个位置都被占时，这个码认的是另一位成员自己的位置（`REJOIN`），陌生人进不来，以前的记录也还是 TA 的。
5. **第一眼体面**：两台都在「我们」页点「取个名字」，各自填自己的称呼并保存。名字会同时出现在两个人手机上。**她打开应用的第一眼不能是「未命名」**——这一步没做完就不要写任何内容。
6. 打开「回看与通知」，确认两件事都在她想要的位置：每周回看的星期与时间（默认周日 20:00）、对方写了新的。Android 13+ 会在这一刻请求通知权限。

## 2. 当天：写下第一页，并当场验证互见

1. 在她的手机上，从解锁开始**计时**写一条纯文字记录：记下实际秒数和交互数，目标是 ≤10 秒、≤4 次交互（H1）。**这两个数字必须写进 `docs/testing/real-use-log.md`，凭手感说"挺快的"不算**。此后任何让数字变大的改动都算回归。
2. 点发布。另一台手机上等它自己出现（Room `Flow` 持续收集，不需要切 tab 触发刷新）。出现之后：
   - 正文是正文，不是标题；
   - 作者显示成她的名字，不是「未命名」也不是「TA」的通用占位；
   - 带图记录里图片真的显示出来；
   - 在她手机上回一句评论，能在对方那台看到。
   这一步是 E1 的真机部分：夹具早就绿了，缺的是"两台真机互相看见"。
3. 写进 `docs/testing/real-use-log.md`：开始日期、用的真机还是具名模拟器（设备名 + Android 版本）、计时数字、当天已知缺陷清单。已知缺陷不影响开档，影响的是你还记不记得它们。

## 4. 出问题时按这个顺序自救

1. **对端进不来**：让对方重装后走「我是伴侣」+ 新配对码；如果她才是第一位且她的会话没了，直接重新 bootstrap 找回自己的槽位。
2. **两台都进不来**：在服务端本机跑 `SessionAdminCommand`（README §会话恢复）。这一步只在服务端那台机器上执行，且它显式关闭 web，不可能和正在服务的进程并行。
3. **怀疑数据被写坏**：先用 `scripts/backup.sh` 存一份当前状态（坏数据也要留档），再从最近一次好备份恢复到**新的空库**比对，不要原地覆盖。
4. **数据库整库要重建**：`restore.sh` 只接受空目标库；恢复后核对第 0 节那条 SQL 的计数。

## 5. 这一天不得说的话

- 不得说"M1 完成"或"可以交付了"。开档 = 真实使用**开始**，验收人是伴侣本人，判据是她真用起来。
- 不得把 Robolectric / JVM / 真库测试当作真机证据；两类证据在验收记录里分行写。
- 不得因为链路绿了就提前宣布共同记录扩展、媒体、备份 UI 或视觉完成。
- 不得加任何统计形态的东西：条数、字数、活跃天数、间隔、已读回执、"对方没写"提示，**包括设置项、调试入口和本地统计**。
- 密钥只留在服务端本机环境或未提交的 `.env`；配对码、会话令牌、真实记录正文一律不进 git、不进日志、不进截图。
