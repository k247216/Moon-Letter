# 月笺的人类尺度原则

状态：长期有效，跨里程碑适用，不因 M1/M2 换版而失效
适用范围：产品范围决策、优先级排序、验收口径
与其他文档的关系：本文件规定**取舍方向**；`docs/superpowers/specs/` 规定**必须做什么**。规格中具体的数字、字段和流程条目优先于从本文件推出的结论——本文件不用于绕过已写明的规格要求。但两处冲突若落在下面这些主题上，不得默默按规格继续实现，必须停下并按交接文档 §8 的格式回传：本文第 1 节的四条成功标准、第 2 节的记录成本、第 4 节的记分牌禁令、第 5 节的可带走性、第 7 节的使用者所有权。回传后修订规格或修订本文，二选一，不留下互相矛盾的权威文档。

这份文档存在的原因：月笺只有两个用户。几乎所有软件工程默认假设（用户量、留存曲线、可回滚的测试数据、随时可修的运维）在这里都不成立，而这里真正的风险恰恰不体现在任何测试报告里。

## 1. 唯一判据

这个产品只有四条成功标准，其余都是虚的：

1. 两个人真的在用；
2. 一年后还在用；
3. 数据不丢、不错、不被人拿走就看不到；
4. 记录一次生活，比在微信里发一张照片更费力不多。

架构纯度、测试数量、与参考图的像素差、里程碑完成度，都不在上面四条里。任何一项工作如果无法说明它如何服务上面四条，默认降级。

## 2. 记录成本是产品本体，不是体验优化

日记的价值不在书写那一刻，而在多年后翻到的那一刻；而它能不能存在，取决于某个疲惫的晚上那个人愿不愿意多花十秒。

- **每一次额外的书写摩擦，都用缺失的日子付账。** 错过的一天无法补写，也无法 retroactively 产生。
- 因此要求：进入记录不需要选择媒介类型、不需要必填字段、单一输入框、自动保存草稿、从编辑到落本地不超过两步。
- **接住已经发生的事，比邀请新的创作更重要。** 伴侣已经在微信/相册里交换的内容本来就存在，只是散落在不可翻阅的地方。系统分享入口（把一张已经发出去的照片变成一条记录）的记录成本接近零，其优先级高于任何"更好的编辑器"。
- 衡量方式：从解锁手机到一条记录保存成功，秒表计时，目标 ≤ 10 秒。这个数字进验收表，比 UI 一致性更早被检查。

## 3. 反馈失真是这个项目的默认状态

被服务的对象是亲密的人，而亲密的人不会用"我不喜欢"来回报你花掉的晚上。所以你会持续收到善意、真实感不足的评价，它比没有反馈更危险。

约束实现方式的三条规则：

- **看行为，不问意见。** 判断依据是"这周有几天是对方在没有被提醒的情况下自己打开的"，不是"对方说挺好"。
- 需要取舍时给**两个具体版本让对方二选一**，不要给一个成品征求意见。选择题的诚实度远高于评价题。
- 任何"我们做得怎么样了"的冲动，都转成上面那条行为指标，不转成产品功能。

## 4. 不做关系记分牌

已经禁止打卡和连续天数，这里补上更细、也更容易手滑的边界。

原则：**单次信号可以有，聚合统计不能有。** 对方点进来"看过了"是温度；"本月 TA 写了 2 篇 / 你写了 11 篇"是税。

明确不做：

- 任何一方的记录条数、字数、活跃天数、间隔天数的统计或排名；
- 已读回执的列表化展示（谁在何时打开过什么）；
- "对方很久没写"任何形式的提示、提醒或暗示；
- 双人进度、共同成就、目标完成度；
- 把"本周小结"做成评价性内容（只做事实回顾，不做评分、比较、趋势判断）。

允许做：一条记录被对方看过时的一次性、不可累积的轻量标记。

## 5. 存档的可读性优先于系统正确性

自托管系统的寿命通常等于维护者的耐心，而不是代码质量。三年后你可能不再想碰这套服务，但那时这份记录才刚开始变得珍贵。

- 目标不是"服务端永远在线"，而是"**在任何一台电脑上都能重新打开这份档案**"。
- 因此：导出不是收尾功能，而是产品主能力；导出格式必须能在不依赖本项目任何代码的情况下被阅读（浏览器 + 纯文本 + 图片文件）。
- 备份介质本身装着全部私密内容与媒体，需要独立加密与访问控制；否则泄露面只是从服务器移到了备份目录。
- 手机双端副本不是备份。物理清理永远晚于备份保留期。

**待决事项（需要产品所有者拍板，实现方不得自行选择）：** 主数据表示是"PostgreSQL 权威 + 强制全量导出"，还是"文件（Markdown/JSON + 原始媒体目录）即权威、数据库只是索引"。后者能把幂等键、游标并发、冲突语义这一整族难题降级成"两个写作者往一个只追加的文件集合里写"，代价是失去强事务与关系约束。默认按前者执行，直到本条被明确改写。

## 6. 连续性优先于完整性

这个产品最怕的不是崩溃，是**断**。一条记录断了，断掉的日记很难重新开始。

- **TA 必须能在你不在场时使用它。** 装好、登录、出错能自行恢复、你忙或出差时它照常工作。任何"需要维护者手动介入才能继续用"的设计都算缺陷，不算便利性问题。
- 因此必须有：离线时可读取全部已缓存内容；写入永不因服务端不可达而失败；会话恢复有一条不需要旧设备的路径。
- **给这个项目设投入上限和开始日期。** 三功能但每天在用，胜过三十功能但还差最后一轮验证。计划里每一个"等 X 完成后开始用"的隐含假设，都要当作一次真实的损失来审查：延后一周开始，就少一周真实记录。
- 真实内容一旦出现，迁移纪律立即生效：此后所有 migration 必须向后兼容或有演练过的回滚，且在独立的**含真实数据的副本**上先跑一遍。"反正是测试库"这句话在此之后不再适用。

## 7. 让使用者拥有它的一部分

礼物和家的区别，是家里有对方的手笔。

**所有权 = 可修改性，不是空白。** 让使用者在开始使用之前先配置一切，只是把成本从实现方转嫁给使用者，结果是第一天就没写下记录。真正的所有权是：**默认值现在就能用，而任何东西在第三年的某个下午都能被 TA 改成"自己的"**，不需要找人、重新构建或重装应用。

- App 名称、TA 的身份色、首页封面、页面里的措辞默认值，决定权交给使用者，而不是由实现方或参考图固定。
- 但"能改"必须是产品能力：这些项都要在应用内可达，改动不得破坏已有内容，也不得要求开发介入。**只存在于源码常量里的可定制项不算可定制。**
- 反过来，少数门一旦有真实内容就关上了，必须在第 0 阶段定：Android 桌面图标名称（launcher 在安装时读取标签，用户不能自由输入，只能用预先声明的有限候选或在下一版构建里定名）、导出格式与文件名约定、change feed 的语义。其余一律留给以后改。
- 所以"名称归使用者"要如实降级：应用内的称呼、封面、身份色和措辞自由；桌面图标名给候选，并向使用者说明这一项为什么受限。
- 视觉验收的标准不是"和参考图像"，而是"**像纸、像 TA 的、不像软件**"。参考稿与代码是同一天产出的，把复刻自己未经检验的想象当成成功标准，是这个项目最容易陷入的空转。

## 8. 重新相遇比记录更早

时间线是记录，回看才是回报。真正会让人停留的瞬间是"一年前的今天 TA 写了什么"。

- 因此"每周回看一条旧记录"（无 AI、无聚合、无评分，只挑一条更早的记录在固定时间出现一次）属于**早期能力**，不属于 M3。它的基础设施要求极低，情感回报极高。
- 反过来，把"过去的今天/本周小结/相册/地图"整体排到最后，是按工程依赖排的，不是按人的收益排的。排期时可以沿用工程顺序，但不能因此认为这些是锦上添花。

## 9. 冲突时怎么选

两个方案都能工作时，按这个顺序让路：

0. **先分辨这个决定是不是单向门。** 可逆的、偏好性质的（名称、颜色、封面、措辞、页面细节）不要现在定，把它做成"以后能改"并把默认值给好；早前的决定很贵，只花在会关上的门上（导出格式、身份与恢复机制、有真实内容后的数据语义）。
1. 降低记录成本 > 增加功能；
2. 保证数据可读可带走 > 保证系统优雅；
3. 保证断掉后能自己接上 > 保证不发生变更；
4. 对方的偏好 > 参考图；
5. 今天开始用 > 更晚上线但更完整；
6. 以上都不牺牲时，才谈工程美感。
